3 · Main bottleneck

Presence scales quadratically

useParticipants(roomId) — livekit_react_hooks.tsx:491

Every client subscribes to postgres_changes on room_participants and, on any change, re-runs a full select * plus a profiles lookup. With N attendees joining, the k-th join is refetched by all k clients already present.

refetches = Σ k for k = 1 … N ≈ N² / 2 N = 300 → 45,150 change deliveries × 2 queries each ≈ 90,000 Postgres queries + 45,150 per-subscriber RLS checks in Realtime

Invisible at ten people, catastrophic at three hundred — and it lands precisely during the mass-join burst you asked about. Either the Realtime layer throttles (stale rosters, hands, reactions) or Postgres does. It compounds with cursor sharing, which alone can emit 9,000 messages a second through the same quota.

5 · Scenarios

Media path yes. The platform fails on the presence layer, not on LiveKit.

no — and no configuration makes it yes. Every viewer would receive 300 full-res streams. Not a BeeHive limit; physics. BeeHive additionally lacks the adaptive streaming that would make even ~25 tolerable.
300 publishing audio + video
no
AI Note Taker at 300
unaffected — one egress, guarded.

On "unlimited users per room": LiveKit Cloud's figure describes the SFU's fan-out, which was never the constraint. It means unlimited subscribers, not unlimited simultaneous publishers — the receiving browser still has to decode every published stream, so the cameras-on ceiling is set client-side on Cloud and self-hosted alike.

P1 — strongly recommended

Enable adaptiveStream and dynacast

One option at RoomPage.tsx:401. Off-page tiles stop pulling full-res video; publishers stop encoding unused layers. Low complexity, no behaviour change in small rooms.

A real audience role

Issue canPublish: false tokens to attendees by default with host-granted promotion. A conference mode is technically necessary: today's uniform-publisher model is only safe because attendees choose not to unmute. Medium complexity.

Virtualize the participants panel

300 rows re-rendering on every roster event is the one frontend cost that grows linearly and visibly.

P2 — optimisation

Batch join/leave system chat rows

Or move them to the data channel alongside reactions.

Cap RoomAudioRenderer to active speakers

Bounds audio elements and decodes regardless of how many people unmute. Addressed by the 20-live-mic cap in v1.0.299.

7 · Answers

The ten questions, directly

  1. Architecture: LiveKit Cloud mesh SFU for media; a single Express process for tokens; Supabase Realtime for presence, chat and every in-meeting signal.
  2. Current participant limit: none configured anywhere.
  3. Practical capacity: ~50 comfortable, ~100 at the edge.
  4. Main bottleneck: the N² presence refetch in useParticipants, compounded by Supabase Realtime quotas.
  5. 300 with cameras/mics mostly off: media yes; blocked by the presence layer until P0 is done.
  6. 300 with cameras on: no, and no configuration changes that.
  7. 300 publishing audio and video: no.
  8. AI Note Taker: does not affect scalability.
  9. Load testing: 350 simultaneous joins, zero failures, p99 6 s — the backend is not the constraint.
  10. Required before a production event: P0 items 1–4. After P0 + P1, 300 in audience mode is realistic.
